# Pi-hole

DNS for the whole LAN, with ad and tracker blocking, plus DHCP and local names.
Image `pihole/pihole:2026.07.2` (Pi-hole v6).

## What's configured, and where

Everything is set with `FTLCONF_*` variables in `docker-compose.yml`. Pi-hole applies
them on every start and shows them read-only in the web UI. To change a setting, edit
the compose file (or `.env.local`) and recreate the container. Blocklists, groups and
per-client settings are not in the compose file; they live in the data directory.

| Setting | Value | Why |
|---|---|---|
| Upstream | Unbound, `172.31.53.2#53` | Recursive resolution at home; no third-party resolver |
| DNSSEC | off in Pi-hole | Unbound validates; validating twice only adds latency |
| Local names | fleet nodes, as `name` and `name.lan` | Generated from `NODE_IPS` by `setup-secrets.sh` |
| App host names | `<name>.${DOMAIN}` → the node whose Traefik serves it | Generated by `setup-secrets.sh` from every Traefik router rule in the repo |
| IPv6 answers | filtered (`filter-AAAA`) | Stops IPv6-preferring clients bypassing a local record via a public AAAA |
| DHCP | enabled in Compose; 7-day leases | Sieve is the sole DHCP server |
| Static leases | every node's cloned MAC → its IP | Generated by `setup-secrets.sh` from `init/purrbrews-mac.sh` |
| NTP server | off | The host keeps time; nothing should answer on port 123 |
| Web UI | port 8080, IPv4 only, no password | Behind sieve's Traefik + Authelia; firewall allows only `sieve_edge`. IPv6 bind dropped 2026-09-17 — see below |

Data: `/srv/data/pihole/etc-pihole` (gravity database, query log, `pihole.toml`).

## First start

```bash
./compose.sh pihole up -d
docker logs pihole | grep -E 'FTLCONF|WARN|ERR'   # every FTLCONF line should show [✓]

dig @192.168.0.10 cloudflare.com +short          # an address: Pi-hole → Unbound works
dig @192.168.0.10 dnssec-failed.org              # SERVFAIL: DNSSEC validation works
dig @192.168.0.10 percolator +short              # 192.168.0.11
dig @192.168.0.10 gatus.${DOMAIN} +short         # 192.168.0.10 (sieve's Traefik)
dig @192.168.0.10 doubleclick.net +short         # 0.0.0.0: blocking works
```

Disable DHCP on both routers before the first start. Sieve advertises the two
fleet DNS servers through its generated DHCP option.

## Handing over DHCP

Running two DHCP servers on one LAN causes intermittent faults that are hard to trace.
Do this in one sitting:

1. Confirm UFW allows `67/udp` from **any**: `sudo ufw status | grep 67`. A client's
   first request comes from `0.0.0.0`, so a LAN-scoped rule silently drops it.
2. Turn DHCP **off on every router/other server**, leaving only sieve responsible.
3. Check the range and lease in `.env.local`, then run
   `bash enable-dhcp.sh --routers-dhcp-disabled` from `stacks/sieve`.
4. Existing leases move over as they renew. To test right away, renew one client
   (`sudo dhclient -r && sudo dhclient`, or toggle Wi-Fi) and check it appears under
   Settings → DHCP → Currently active leases.
5. Watch a couple of days before trusting it: phones, TVs and anything with a
   reservation.

**Break-glass:** if sieve will be down longer than the lease grace period (~3.5 days),
ensure sieve cannot start its Pi-hole, then enable the router's DHCP temporarily.
Disable router DHCP again **before** bringing sieve's Pi-hole back: Compose will
automatically enable DHCP. Do not rely on the obsolete env switch to disable it.

## App host names

Nothing to maintain by hand. When any node's Traefik gets a new router, run
`./setup-secrets.sh` on **sieve**, then `./compose.sh pihole up -d`. Every router
rule ``Host(`<name>.<domain>`)`` becomes `address=/<name>.${DOMAIN}/<that node's IP>`.
It is read from three places, one line per rule:

- `stacks/*/traefik/dynamic/*.yml`: `` rule: Host(`<name>.{{ env "DOMAIN" }}`) `` (sieve style);
- `stacks/*/traefik/config/*.template`: `` rule: "Host(`<name>.${DOMAIN}`)" ``;
- `stacks/*/*/docker-compose.yml`: `` traefik.http.routers.<r>.rule=Host(`<name>.${DOMAIN}`) `` (percolator style).

Check what's generated with
`grep PIHOLE_DNSMASQ_LINES .env.local`.

A name with no record isn't overridden: it resolves through public DNS (the tunnel,
if it's published there) or not at all. So if a new app gives `NXDOMAIN` at home,
this step is the one that was missed.

## Adding names and reservations

Put extra devices in `.env.local`, then re-run `./setup-secrets.sh` (it rebuilds the
generated lists) and `./compose.sh pihole up -d`:

```ini
PIHOLE_DHCP_EXTRA_HOSTS=aa:bb:cc:dd:ee:ff,192.168.0.20,roastery;11:22:33:44:55:66,192.168.0.30,printer
PIHOLE_DNS_EXTRA_HOSTS=192.168.0.20 roastery
```

Keep static addresses outside the DHCP range (`.50`–`.250` by default).

## Known allowlist exceptions

Blocklists/gravity live in the data directory, not in this compose file (see the
table above), so they don't survive in git — this section is the record of what's
been allowed and why, so a gravity rebuild or fresh bring-up doesn't silently lose it.

**Azure Virtual Desktop / Windows App (added 2026-09-17).** The office VDI client
(Windows App, connecting to a Cloud PC/AVD) stopped resolving several
`*.wvd.microsoft.com` hosts on Wi-Fi — confirmed via the client's own
"check access" screen: `afdfp-rdgateway-r1.wvd.microsoft.com` (gateway) and
`rdweb.wvd.microsoft.com` (resource discovery) both unreachable, `www.wvd.microsoft.com`
and `res.cdn.office.net` degraded. Every other required Microsoft endpoint
(`login.microsoftonline.com`, `graph.microsoft.com`, `aka.ms`, etc.) was fine — this
is specifically the `wvd.microsoft.com` family and `cdn.office.net`, most likely
caught by a tracker/telemetry blocklist that doesn't distinguish AVD's own
infrastructure from Microsoft telemetry hosts.

Fix (on sieve):
```bash
docker exec pihole pihole allow --regex '(\.|^)wvd\.microsoft\.com$'
docker exec pihole pihole allow --regex '(\.|^)cdn\.office\.net$'
docker exec pihole pihole reloadlists
```
Verify with `docker exec pihole pihole query <hostname>` for each of the four
hostnames above, or re-run the Windows App client's "check access" screen.

Microsoft's full required-FQDN list for this client is wider than just these two —
see [Required FQDNs and endpoints for Azure Virtual Desktop](https://learn.microsoft.com/en-us/azure/virtual-desktop/required-fqdn-endpoint).
Only `wvd.microsoft.com` and `cdn.office.net` have actually been seen blocked here;
allow the rest proactively only if they start failing too, so this list doesn't grow
into a blanket Microsoft exemption for domains gravity was never actually catching.

## Caveats

- **No IPv6, anywhere, on purpose.** This LAN doesn't use it. `filter-AAAA`
  already stops name lookups from handing out IPv6 addresses; as of
  2026-09-17 the webserver's own `FTLCONF_webserver_port` is IPv4-only too
  (`8080o`, not `8080o,[::]:8080o`) for the same reason — an IPv6 bind with
  no matching `ufw` rule in `../firewall.sh` is a hole, not a convenience.
  Same fix applied to mochaPot's secondary Pi-hole. If a future Pi-hole
  image reintroduces the `[::]` half of the default port string on
  upgrade, drop it again.
- **An overridden name answers only A records.** Other record types for that exact
  name (`AAAA`, `TXT`) get `NXDOMAIN` on the LAN. Browsers don't care. Names without a
  record, and the apex, are untouched.
- **No password on the UI or API.** Only the firewall rule for port 8080 and
  Authelia in front of Traefik keep it closed. Never open 8080 to the LAN, and never
  route it through the tunnel.
- **Client DNS failover is slow.** Most clients wait for the primary to time out
  before trying a secondary. A sieve outage feels like slow browsing, not a clean
  switch.

## Refresh local app DNS

Both resolvers use the same generated split DNS. From the repository root, run
`bash stacks/_lib/refresh-dns.sh sieve` as the ops user, then recreate this
Pi-hole with the node's compose wrapper. A restart alone does not update its
environment. Keep NODE_IPS, DOMAIN and PIHOLE_DNS_EXTRA_HOSTS consistent on both
nodes. See [the network audit](../../../docs/network-audit.md) for rollout order
and checks; verify the secondary from another LAN machine before advertising it.

## Activate DHCP after router handover

Sieve is permanently the primary DHCP server: its Compose file fixes
`FTLCONF_dhcp_active: "true"`. mochaPot fixes the same setting to `"false"`.
The legacy `PIHOLE_DHCP_ACTIVE` env key is ignored and may be removed.
After disabling DHCP on every router/other server on the LAN, run as barista:

```sh
bash /opt/purrbrews/stacks/sieve/enable-dhcp.sh --routers-dhcp-disabled
```

This backs up node-local settings, refreshes DNS records and the advertised DNS
servers, validates the IPv4 lease range, uses the fixed DHCP role in Compose, recreates
Pi-hole and checks both its active setting and UDP port 67. Changes to the
script travel via Git; `.env.local` remains generated node-local configuration.
Firewall port 67 must already be allowed by the node's tracked firewall script.
Reconnect one affected client first and confirm a usable lease before renewing
everything. DHCP cannot cross a separate routed/isolated IoT subnet without a
relay or a DHCP service on that subnet.
